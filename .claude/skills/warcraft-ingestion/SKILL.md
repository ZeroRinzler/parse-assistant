# warcraft-learner ingestion & content pipelines

Ingestion is the Angular app itself, booted with the `ingest` build configuration - there is no separate ingestion codebase. The orchestrator and its discovery helpers live in `frontend/src/app/ingest/**` (bundled only by the ingest configuration, so the production shell never carries them). Two plain-Node scripts under `frontend/scripts/` support it and carry **zero ingestion logic**: `ingest-server.js` (an Express file store on :3000 - REST over `public/data/`: `GET`/`PUT`/`DELETE /api/data/{path}` plus `GET /api/dirs/{path}` listings, path-contained, atomic writes) and `ingest-headless.mjs` (the CI harness). Rulebook generation is the **warcraft-rulebook** skill; this skill covers how ingestion consumes rulebooks.

Two entry points (both listed in CLAUDE.md):
- `npm run start:ingest` - interactive: runs the file server + `ng serve --configuration ingest`; open http://localhost:4200 and watch the browser console. Run `npm run data:pull` first so signature-skip has the current published data to compare against.
- `npm run ingest` - headless (what `ingest-parses.yml` runs hourly): the harness starts both processes, drives the app in headless Chromium (Playwright), pipes the app console to stdout, waits for the orchestrator's `globalThis.__INGEST_DONE__` summary and exits 0/1. WCL auth is the environment file's embedded public pair (see the warcraft-wcl-data skill).

Both entry points serve with the dev-server watcher **off** (`watch: false` on the ingest serve configuration, and `public/data` excluded from the ingest build's assets): the orchestrator writes into `public/data/specs/`, and a watching dev server would rebuild + live-reload on every write, restarting the run from scratch in an endless loop. After a code edit, restart `start:ingest` by hand.

## Ingestion flow

The ingest environment's app initializer fire-and-forgets `IngestOrchestratorService.run()` (`src/app/ingest/ingest-orchestrator.service.ts`), which drives the SAME five `*TransformService`s the runtime uses, persisting through the SAME `DataFileApiService` (bound to `IngestHttpDataFileTransport`, which reads and writes through the file server). There is no separate analysis pipeline. Before discovery it resolves the full spec universe (class/spec names + slugs, icons) from WCL `gameData.classes` (`mapClassesToSpecMeta`), hydrates the runtime's spec-meta cache so `getRankings` resolves, and bakes `spec-meta.json` (each spec's icon comes from its rulebook's `spec_icon`).

1. Reads each spec's `rulebook.json` and feeds its cooldown/defensive/rule ids to the transforms; there is no code-side validation - the schema (in the warcraft-rulebook skill) is the contract the generating agent follows, and the ids are grounded against WCL when the rulebook is generated.
2. Discovers the specs that have a `rulebook.json` and the current live encounters (`getEncounters`: `worldData` discovery + a cheap rankings liveness probe). **Spec work-order** (`ordering.ts`, all cheap file-server reads, zero WCL budget): empty specs first, then **old-version** specs (any on-disk file below the current `INGEST_VERSION`), then **current-version** specs, randomized within each group (`PRIORITY_SPEC` pinned to the front of its bracket). So a budget-bounded run fixes the most out-of-date data first.
3. Per encounter: asserts remaining WCL budget, fetches rankings (cheap), computes a version+ranking `source_signature` (`sha256(INGEST_VERSION + parse-set fingerprint)`), and **skips** the encounter when the signature matches the stored stamp. `INGEST_VERSION` (`src/app/ingest/ingest-version.ts`) is a **manual integer**: bumping it invalidates every cached file. Because transform-file edits do not auto-invalidate, **bump `INGEST_VERSION` as part of any change that should produce different tailored data** (transform math, rulebook semantics, a deliberate refresh). The live value is the integer exported from `ingest-version.ts`.
4. Otherwise runs the five transform services (`burst`/`rotation`/`defensive`/`gear`/`map`) under bounded concurrency. Each fetches the parses it needs (`Casts`/`Buffs`/`DamageDone`/`DamageTaken`, plus `includeResources`/`hostilityType` events for positions) via the shared cached `WclApiService` and computes its slice. The WCL response cache (ng-http-caching, memory store) is cleared between encounters to bound memory.
5. Writes the stamped per-slice tailored files (`{spec}/{burst,rotation,defensive,gear}/{enc_id}.json`) and per-parse position timelines (`positions/{enc_id}.json`); every file carries both `source_signature` and the bare `ingest_version` integer.
6. Rebuilds the `{spec}/encounters.json` and top-level `index.json` indexes, then prunes stale encounters.

The data files are written **minified** (no pretty-print): machine-read only and thousands of them, so dropping indentation cuts the footprint ~70% while staying valid JSON. The Angular HttpClient serializes write bodies compact and the file server (`scripts/ingest-server.js`) stores them verbatim; `rulebook.json` stays pretty (hand-authored).

`frontend/public/data/specs/**` is **not tracked on `main`** (it is gitignored there). It lives once on the **`gh-pages` branch at the site root under `data/specs/`** - the single shared copy the deployed site serves, and `ingest-parses.yml` is its only writer. Each run overlays the current `origin/gh-pages` `data/specs/` copy into the working tree before ingest (so signature-skip has the latest data on disk to compare against - `git archive origin/gh-pages data/specs | tar -x`), then publishes the resulting `frontend/public/data/specs` back to `data/specs/` on `gh-pages` via a single-commit, target-folder-scoped deploy (`clean:true` replaces `data/specs/` only, never `main/` or the `pr-*` previews). The action commits nothing when the tree is byte-identical, so quiet hours produce no push. The site reads this copy directly (absolute `dataBaseHref`), so publishing the data **is** the deploy - no code rebuild needed, and code deploys (`deploy-pages.yml`, which builds only app shells) never re-push the dataset. Both `gh-pages` writers (`ingest-parses`, `deploy-pages`) share **one `gh-pages` concurrency group** so their single-commit force-pushes serialize instead of reverting each other. For local dev, run `npm run data:pull` (from `frontend/`) to fetch and extract the data into your ignored working tree.

> **Keep data shapes in sync.** Because ingestion runs the very same `*TransformService`s the runtime uses, the tailored slice shapes are defined in exactly one place - each slice's `*Bench` interface (its `*-data-source.ts`) plus the relevant `core/models/*` - and ingestion writes precisely those, so the slice shapes stay in sync automatically. Changing a slice's `*Bench`/model therefore updates runtime and ingest at once (one implementation). You still keep the rulebook schema (`rulebook.schema.json` in this skill's directory) in sync with the transforms (they consume the rulebook's `duration`/`spell_id`s) and with the **warcraft-rulebook** skill that generates rulebooks. The data-file shapes are defined in code - see "Data file shapes" below. Already-committed JSON under `data/specs/**` keeps stale fields until the next re-ingest - harmless, since consumers ignore unknown fields.

## Rulebooks
Rulebook generation is the **warcraft-rulebook** skill (SimC + Wowhead + WCL grounding, one isolated subagent per spec). Ingestion consumes them directly:

1. **Consume**: each spec's `rulebook.json` is read and its ids/durations feed the transforms. There is no code-side validation - the schema (in the warcraft-rulebook skill) is the contract, and ids are grounded against WCL when the rulebook is generated. The schema asks for at least one `major_cooldowns` and one `defensives` entry.
2. **Publish**: rulebooks are gitignored on main and live on gh-pages. Publish the generated `rulebook.json` files into the gh-pages `data/specs/` tree; the scheduled ingest runs then read them and rebuild that spec's benches over their next passes.

## Data file shapes

The data files ingestion writes are deliberately **not** schema-documented here - read each shape from its source of truth so the docs cannot drift:

- **Rulebook** (`rulebook.json`) - `rulebook.schema.json` in this skill's directory: the authoritative contract the generating agent follows; generation is the **warcraft-rulebook** skill. All spell IDs come from the rulebook, never hardcode spec-specific IDs. The rule-engine condition kinds (`cast_without_prior`, `hold_cooldown_for_anchor`) are defined in the schema and the rotation rule-engine code.
- **Slice benches** (`{burst,rotation,defensive,gear}/{enc}.json`) - each slice's `*Bench` interface in its `*-data-source.ts`, plus `core/models/*`.
- **Indexes** (`index.json`, `spec-meta.json`, `{spec}/encounters.json`) - `core/models/*` (incl. `spec-meta.models.ts`) and the orchestrator's `rebuildEncountersIndex`/`rebuildSpecIndex` + spec-meta bake.
- **Signature stamps** (`source_signature`, `ingest_version`, on every slice + positions file) - `src/app/ingest/ingest-version.ts` + `signature.ts`.
- **Positions** (`positions/{enc}.json`) - `core/models/positioning.models.ts`; see the **warcraft-wcl-data** skill for the WCL position/facing-unit quirks behind it.
